# Pueue Work Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The planner queues the agreed steps in pueue. `pi-wait` tasks release each step when a concrete fact holds. Every event is logged per workflow.

**Architecture:**
- One Python CLI, `scripts/pi-queue`, does 4 jobs:
  - `add` expands a template into pueue tasks.
  - `run-step` executes one step, through the `shell`, `pi` or `claude` executor, then releases its successors.
  - `wait` checks one fact, then releases.
  - Every event is logged.
- `scripts/pi-wait` is a 2-line shell entry point for `pi-queue wait`.
- Templates live in `scripts/pi-queue-templates.json`.
- The `/pi` Monitor groups queue tasks by their label.

**Tech Stack:** Python 3 (stdlib only), pueue 4.0.4, `gh`, herdr, session-band (TypeScript, `claude plugin test .`).

**Spec:** `SPEC.md` (approved, branch `feat/pi-queue`)

## Global Constraints

- Labels: `q:<session>:<template>:<step>`. `<session>` is the planner's Claude session id; `<step>` is the step's name in the template.
- Future steps are created with `pueue add --stashed`. Waits go in group `waits`, created with `pueue group add waits` plus `pueue parallel 20 --group waits` when missing.
- Release is `pueue enqueue <id>…` with explicit ids only. Never call `pueue enqueue` without ids.
- Every `pueue add` goes through `pueue` on PATH, which is the pueue-safe wrapper.
- Events go to `~/.local/state/pi-queue/events.jsonl`, overridable with `PI_QUEUE_STATE`. One JSON object per line: `{time, session, workflow, template, step, executor, event, task}`, plus `round` for Pi steps. `event` is one of `released`, `failed`, `notified`, `picked-up`, `started`, `done`. The `workflow` default is `gated`.
- Executors:
  - `shell` runs its `cmd` list with no model.
  - `pi` runs `pi-view --tui pi --model <model> --session-id pueue-<slug> -p "$(cat <brief>)"` in the step's worktree.
  - `claude` delivers a brief file.
- Claude fallbacks: `wait` (default), `sonnet` (`claude -p --model sonnet "$(cat <brief>)"`) or `opus`.
- Wait polling: every 10 s, timeout 24 h. A template may override both; tests pass short values.
- Test seams (env overrides): `PI_QUEUE_PUEUE`, `PI_QUEUE_GH`, `PI_QUEUE_AC_RUN`, `PI_QUEUE_PI_OUTCOME`, `PI_QUEUE_HERDR`, `PI_QUEUE_CLAUDE`, `PI_QUEUE_PI_VIEW`. Each defaults to the real binary.
- Never automate push to main, merge, approvals, force-push, branch deletion, `reset --hard` or `pueue clean`.

## Review Focus

1. A wait whose fact can never hold (PR closed, run killed) must fail and release nothing. Tests: `test_pr_merged` (closed case) and `test_outcome` (killed case).
2. A step that fails must not release its successors. Test: `test_step_failure_releases_nothing` in Task 3.
3. A `pi` step into a busy worktree must fail without starting Pi. Test: `test_worktree_guard`.
4. Running `pi-queue add` twice must create 2 independent queues, not double-release one. Test: `test_two_adds_are_independent` in Task 3.
5. Typing into a Claude pane that is mid-turn must not happen. Test: `test_claude_step_routing` (busy-pane case).

### Task 3: `pi-queue add` and `run-step` — AC-6 to AC-12

**Files:**
- Modify: `scripts/pi-queue`.
- Create: `scripts/pi-queue-templates.json`.
- Test: `scripts/tests/test_pi_queue.py`.

**Interfaces:**
- Produces:
  - `pi-queue add <template> key=value… [workflow=gated] [session=<id>]` prints `<label> <task id>` per created task.
  - `pi-queue run-step <step json file>` executes the step; on success it enqueues the step's `release` ids. The step file lives under `PI_QUEUE_STATE/steps/`.
- Template contents. Steps run in order unless noted; `{x}` is a parameter.
  - **`pr-merge`** (params: `pr`, `repo`, optional `post`, a `;`-separated list of commands):
    1. wait `pr-merged {pr}`
    2. shell `git -C {repo} pull --ff-only`
    3. a shell step per `post` command
  - **`spec-approved`** (params: `spec`, `worktree`, `brief`):
    1. wait `spec-approved {spec}`
    2. claude step "write the plan" (`brief`, fallback `wait`)
    3. pi step dispatch (`model` param, default `opencode-go/deepseek-v4.1-flash:medium`, brief `{worktree}/<plan path>` given by the claude step's output file)
  - **`pi-run-done`** (params: `task`, `worktree`, `branch`, `brief`):
    1. wait `outcome {task} checks passed`
    2. claude step "review commits" (fallback `wait`)
    3. shell step: `git -C {worktree} push -u origin {branch}`, then `gh pr create --draft --head {branch} --fill`
  - **`review-decided`** (params: `worktree`, `run`, `session`, `message`):
    1. wait `review-decided {worktree} {run}`
    2. shell step: `herdr pane send-text` the `message` file into the Pi pane named in `$TMPDIR/pi-view/{session}.pane`, then Enter
  - **`checks-exhausted`** (params: `task`):
    1. wait `outcome {task} checks failed` (round 3)
    2. shell step `herdr notification show "pi#{task} checks failed, needs you"`
- Executor rules:
  - `claude`: find a herdr pane with `agent == "claude"` and `agent_session.value == <session>`.
    - If its `agent_status` is idle, send-text the brief, then Enter, and log `picked-up`.
    - If the pane is busy or missing, `notified` once, then poll every 10 s until idle or timeout.
    - `fallback: sonnet` (or `opus`) runs the headless command instead of waiting.
  - `pi`: before dispatching, refuse (exit 1, `failed` event) when `pueue status --json` has a Running task whose `path` equals the step's worktree.
  - Unknown template: exit 2, nothing created.

  - `test_worktree_guard`, `test_unknown_template_refused`, `test_event_log`
  - `test_waits_group`: group created when missing.
