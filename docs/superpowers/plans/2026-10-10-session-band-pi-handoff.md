Read `session-band-plugin/hooks/register.tsx`, `clear.tsx` and `blast.tsx` first for house style (each feature exports `register(on)`, `register.tsx` calls it; pure logic in plain `.ts`, every `$.*` call in `.tsx`). ## Goal

While Claude Code has handed work to Pi through `pueue`, show it. A hand-off segment in the existing band row, a pane that shows what Pi is doing and lets the person control it, and fast review controls, all inside Claude Code. Today a `pueue` task is invisible and cannot be touched: it runs `pi -p "..." < /dev/null`, so there is no stdin and no way to see progress.

## Already established (spikes run 2026-10-10), do not re-derive

- **pueue.** `pueue status --json` returns `{ "groups": {...}, "tasks": { "<id>": task } }`. A task has `id, label, path, command, original_command, status, group, created_at, envs, dependencies, priority`. `status` is an **object keyed by state**: `{"Done": {"enqueued_at","start","end","result": "Success"}}`; `Running` and `Queued` carry `enqueued_at` (Running also `start`). `result` is a string for success and an object for failure and kill: confirm the exact shapes by running `pueue status --json` against a task you fail on purpose (`pueue add -i -- false`) and a killed one, and put them in your test fixtures. `path` is the task's cwd. `pueue add -i --print-task-id --label <l> -- <cmd>` prints the new integer id and nothing else. Controls: `pueue kill <id>`, `pueue pause <id>`, `pueue start <id>`, `pueue remove <id>`, `pueue clean` (all finished, so do not use it).
- **Dispatch command shape.** `pi --model <provider/id[:effort]> [--no-extensions] -p "$(cat <plan>)" < /dev/null` (a real task, id 21, looked like this). **The new convention (M0): add `--session-id pueue-<slug>`.** A command without it is a legacy task: show it, mark usage "n/a", never guess a session file.
- **Pi session files.** `pi --session-id pueue-x` stores `~/.pi/agent/sessions/<dir>/<ISO time>_pueue-x.jsonl`. `<dir>` is the cwd with the leading `/` dropped, every `/` turned into `-`, wrapped in `--`: `/Users/me/.claude/jobs/ab/tmp` becomes `--Users-me-.claude-jobs-ab-tmp--` (dots kept). **A second call with the same id resumes the same file with history** (tested: it remembered a word from call 1). That is what "Continue" uses.
- **Pi JSONL events.** One JSON object per line. `type` is one of `session` (`id, cwd, timestamp`), `model_change` (`provider, modelId`), `thinking_level_change` (`thinkingLevel`), `message`, `custom_message`. A `message` has `message.role` of `user`, `assistant` or `toolResult`. An `assistant` message has `content[]` blocks of type `text`, `thinking` or `toolCall` (`{id, name, arguments}`; names seen: `read`, `bash`, `edit`, `write`), plus `usage {input, output, cacheRead, cacheWrite, reasoning, totalTokens, cost {input, output, cacheRead, cacheWrite, total}}`, `model`, `provider`, `stopReason` (`toolUse`, `stop`, `error`) and, on error, `errorMessage`. A `toolResult` has `toolName, toolCallId, isError, content[]`. Treat unknown types and tool names as opaque; never throw on them.
- **Mod API limits** (Claude Code plugin engine). `$.process.run(argv, { cwd, env, stdin, timeoutMs })` is one-shot, no shell, no TTY, output capped at 4 MiB, default timeout 30 s. `$.fs` has only `read, write, list, exists, stat`: **no rename, remove, mkdir, no read offset**. So: atomic write is write-to-temp then `$.process.run(['mv', tmp, dest])`; deletion is `['rm', ...]`; **tailing a big file is `['tail', '-c', '+<offset+1>', path]`** with the offset from `$.fs.stat(path).size`. `$.clock.every(ms, fn)` returns `{ cancel() }`. `$.ui.open({ id, title })` opens a pane drawn by `on('ui.render', { component: 'Pane', requestId: id }, ...)`; elements come from `$.ui.resolve(e)` (`Box, Text, Button, Input, Select, Code, Markdown`); `Button` takes `key` and `onPress`; `Input` takes `key` and `onSubmit(value)`; `$.command.register({ name, description })` plus `on('command.run', { command }, ...)` makes a slash command. State is `atom({ plugin: 'session-band', key } as const, initial)` with `read($, a)` and `update($, a, fn)`, each key declared in `types/index.d.ts`.
- **`$` cannot cross an import** and cannot be passed as a value. Pure parsers in `.ts`; all `$` calls in `.tsx`.
- **agent-review files** (per repo, under `.pi/agent-review/`): `mode.json` (`{mode: "on"|"off"}`, absent means on), `pending/<runId>.json` (`runId, base, baseTree, end, endTree, files[{file}], startedAt, endedAt`, optionally `error`, `tamper`), `decisions/<runId>.json`. A `runId` is a UUID. A run launched with `--no-extensions` loads no agent-review extension and creates no pending record: the review state is then simply absent, not an error. **Review state for the band:** a pending record present means `review pending`. After a decision file exists and the pending file is gone: `approved` if the decision has no `patch`, no `notes`, no `skipped` and every file `accepted`, otherwise `changes requested`.
- **Neovim and herdr.** Each running Neovim listens on a socket by default, at `$TMPDIR/nvim.<user>/<random>/nvim.<pid>.0`. `nvim --server <sock> --remote-expr 'getcwd()'` prints that instance's cwd. `herdr pane split --current --direction right --cwd <dir>` returns JSON with `.result.pane.pane_id`; `scripts/pane-handoff` shows the pattern (read it, and run `herdr pane run --help` before using it). `herdr pane current` names the pane Claude Code runs in.
- **Harness quirks (Claude sessions, not your code):** in a worktree-isolated session any Bash text containing `git` is refused, so run git as `/usr/bin/git`; `rtk` rewrites some command output and swallows exit codes, so read output text, not status.

## Decisions (do not reopen)

1. **Tracking is session-owned.** A `tool.call` hook on `Bash` records the call's start time, runs `await next(e)`, and when the command text contains `pueue add`, runs `pueue status --json` once and tracks every task that (a) has `created_at` at or after the call's start, (b) has a Pi dispatch command (`isPiDispatch`), and (c) has a `path` equal to or inside the session cwd or its repo root. Do **not** rely on the Bash stdout: a dispatch is usually `ID=$(pueue add ... --print-task-id ...)` followed by `pueue wait`, and parallel mode adds several. Store `{ id, sessionId?, label?, cwd, addedMs }`. Never scan pueue for tasks the session did not add. Known race: another Claude session adding a Pi task in the same repo within the same moment would be attributed here too; accept it for v1 and note it in the code.
2. **Scope is pueue delegate and parallel delegate only.** Out of scope for v1, and **do not build any of it:** pane-mode hand-offs, live steering of a running Pi (no `--mode rpc`, no stdin channel), a git-diff viewer, editing the dispatch format beyond `--session-id`, a settings UI.
3. **The band is additive.** Do not change what `drawBand` shows today. Append a segment when `summarize(...)` returns one.
4. **Fields.** In the band: task id and state glyph, `model:effort`, elapsed, Pi tokens and cost, files changed, label, review state, and a failure marker with exit code. `model:effort` comes from the session file's `model_change` and `thinking_level_change` events and falls back to parsing `--model` in the command. Pane only: current activity (last tool call), queue position, Pi context fill, per-model cost. With more than one live tracked task the band shows a rollup (`pi 2▶ 1✓`) and the pane lists each.
5. **Lifecycle.** Visible while `Queued`, `Running` or `Paused`. On `Done` with review pending: stays until the decision lands, then shows `approved` or `changes requested` for 30 s. On `Done` with no review: `✓` for 30 s. **`Failed` or killed persists until dismissed** (pane button). Unreachable `pueue` daemon: hide the segment, one debug log line, no UI error. Poll `pueue status --json` every 2 s **only while a tracked task is live**; cancel the timer when none is. Tail session files incrementally by byte offset.
6. **The pane** (id `pi-handoff`, command `/pi`, also opened by a `[pi]` Button in the band segment): task list (with queue position while `Queued`); live transcript of the selected task (assistant text cut to a few lines, tool calls as `edit <path>`, errors flagged, bounded to the last 200 entries; the latest tool call is the "current activity"); a usage line (tokens, cost, context fill % from `usage.totalTokens` against the model's window if known, otherwise omit it; show per-model cost only if the session used more than one model); buttons Abort, Pause/Resume, Remove (finished only), Dismiss; a Continue input that, on submit, writes the follow-up text to a file (`<os tmp dir>/pi-continue-<slug>-<n>.md`, via `$.fs.write`) and dispatches `pueue add -i --print-task-id --label <label> -- pi --model <same model:effort> --session-id <same id> -p "$(cat <file>)" < /dev/null`, the same shape as the existing dispatch, then tracks the new task. **Never put the user's text into the command string**, only the file path. The exact argv that makes pueue run that shell string correctly is an unknown: spike it first (see Traps, "pueue argument joining") and encode what works in `hooks/pueue.ts` with a test. Abort asks for confirmation (second press).
7. **Clean stale.** One pane button, dry-run first. In scope only: tracked pueue tasks and Pi sessions whose file name ends `_pueue-<slug>.jsonl`, both finished (`Done`/`Failed`/killed) and older than 7 days. It lists counts and sizes, deletes only after a second confirm press via `pueue remove <id>` and `rm`, and cleans the mod's own state entries automatically. **Never touch** `.agents/sessions/`, any Pi session without the `pueue-` label, or `~/.pi/agent/sessions` generally.
8. **Review controls** (in the pane, only when a pending record exists for a tracked task's repo): **Open review** locates a Neovim whose `getcwd()` is the repo (or a worktree of it) and runs `:AgentReview` over its socket; none found, it opens one with `herdr` and runs `nvim --listen`. **Approve** calls `agent-review approve <runId>`; on refusal reason `tree-changed` it falls through to Open review and says why. **Reject all** asks for confirmation (second press) then runs `:AgentReviewRejectAll` over the Neovim socket (launching Neovim first if needed). The mod never writes `decisions/*.json` itself and never writes a decision except in an `onPress` handler for one of these two buttons. Check `UiPressArgument` for a provenance field and refuse a press that is not from a person if the type exposes one. The mod reads decisions to update the band; a decision file appearing is the only signal.
9. **House rules:** plain `.ts` for logic, `.tsx` for `$` calls, tests with `claude-code/testing` next to each file, one commit per file group, stage by path. Palette from `hooks/palette.ts`; running = teal, queued and paused = yellow, done = green, failed = red, review pending = yellow, muted for labels.

## Gate contract (Claude builds M6; you stub it)

- `scripts/agent-review approve <runId>`: exit 0 and stdout `{"ok":true,"runId":"..."}` after writing the decision; exit 2 and stdout `{"ok":false,"reason":"tree-changed"|"no-pending"|"invalid-id"|"error","message":"..."}` otherwise. It writes an all-accepted decision only when the working tree still equals the pending record's `endTree`. Never sets `skipped`.
- `:AgentReviewRejectAll` (Neovim): restores every file in the current pending review from its base tree via the existing `M.reject`, then records the decision via `M.done()`. Invoked as `nvim --server <sock> --remote-send '<C-\><C-N>:AgentReviewRejectAll<CR>'`. Success is observed by the decision file appearing.
- Both need the review's `runId` known to the mod from the pending record. Neither is available until M6 lands; your M5 must work with them stubbed and report "gate not available" if the command is missing.

## Traps

- **rtk swallows exit codes.** Read command text, not status. A `pueue` that is not running prints an error and may still look like success.
- **`--session-id` creates the session if the id is new and resumes it if it exists.** A reused slug silently resumes an old session. The slug should be unique per task (plan name plus short id).
- **Parallel tasks share a cwd.** Never choose a session file by newest-in-directory; always by the exact `_pueue-<slug>.jsonl` name.
- **The session JSONL grows large** (a trivial run was 128 KB). Never `$.fs.read` it whole; tail by offset and keep the offset in state.
- **pueue argument joining (unknown, spike it in M1).** Run `pueue add -i --print-task-id -- sh -c 'echo "$1"' x "a b"` and read `pueue log <id>`: does it print `a b` or `a`? That tells you whether pueue shell-escapes each argv element or joins them raw, and so how to pass a `< /dev/null` redirect and a `$(cat file)` through `$.process.run`. If argv elements are joined raw, build the whole dispatch as one pre-quoted string argument that you construct from fixed parts plus a file path with no special characters.
- **`pueue` ids are global to the machine.** Only tracked ids are ever read, controlled or deleted.
- **`pueue remove` on a running task fails or kills.** Gate Remove on a finished state.
- **A Pi run with `--no-extensions` has no review.** Absence of a pending record is normal, not a bug.
- **The review gate protects against self-approval.** If a change makes it easy for the model, not the person, to approve or reject, it is wrong. Stop and report.
