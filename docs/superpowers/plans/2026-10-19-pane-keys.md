# Consistent Mod Pane Keys Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keys pressed in a session-band mod pane stop falling through to the prompt. The same digits jump to any pane. `ctrl+x b`, pressed from the prompt, gives the keyboard to the pane on screen.

**Architecture:** Three changes, applied to all five mod panes (`pi-handoff` in `pane.tsx`, `pi-history` in `history.tsx`, `worktrees` in `worktree-pane.tsx`, `draft-prs` in `draft-prs.tsx`, `gates` in `gates.tsx`):
1. Every hotkey a pane uses is bound in every state.
2. Digits `1`–`5` jump to a pane through the existing `goTo` runner.
3. A focus Button with `action="app:cycleDiffBase"` re-focuses its own pane.

The pure data lives in `pane-nav.ts`.

**Tech Stack:** TypeScript Claude Code plugin (`claude-code` engine, `claude-code/testing` kit).

**Spec:** this plan, approved in chat on 2026-10-19 after a live spike. The spike established:
- A focused pane only consumes keys bound as Button `hotkey`s. Any other key is typed into the prompt and takes the keyboard back.
- While the prompt holds text, the engine refuses `focus` on every `$.ui.open`, so one stray letter breaks all pane switching.
- A Button with `action="app:cycleDiffBase"` is pressed by that action's chord (`ctrl+x b`, the person's choice) from the prompt. Its `$.ui.open({ id, title, focus: true })` then gives the pane the keyboard (`isFocused: true`). It works only for the pane on screen: a Button in a background tab is not pressed.
- `ctrl+x tab` focuses the band, not a pane.

### Task 3: `ctrl+x b` focuses the pane on screen

**Files:**
- Modify: `session-band-plugin/hooks/pane-nav.ts`; the key bar of each of the five panes
- Test: one kit test per pane (or one table-driven test file `pane-focus.test.ts`)

**Interfaces:**
- Produces, in `pane-nav.ts`: `FOCUS_ACTION = 'app:cycleDiffBase'` and `FOCUS_REFUSED = 'Clear the prompt first: ctrl+x b focuses the pane only from an empty prompt.'`

Each pane renders `<Button key={`${prefix}-focus`} plain dimColor action={FOCUS_ACTION} label="ctrl+x b" onPress={() => void focusSelf($)} />`. Here `focusSelf` (local to the pane, since `$` cannot cross an import) does three things:
1. Reads `(await $.prompt.read()).text`. If it is non-empty after trimming, it calls `$.ui.toast(FOCUS_REFUSED)` and returns.
2. Otherwise it awaits `$.ui.open({ id: SELF, title: PANE_TITLES[SELF], focus: true })`.
3. Then it reads `$.ui.panes()`. If the pane is not `isFocused`, it toasts `FOCUS_REFUSED`.

## Revision (2026-10-20)

Exactly one Button holds each hotkey per render; it may be the original action Button or an inactive key-bar holder. Keep all action Buttons' exact keys, hotkeys, labels, handlers and original render conditions:

- `x`: `pi-abort` (`Abort`) when a task is selected and not complete; otherwise `pi-key-abort` (`kill`).
- `h`: `pi-hold` (`Hold queue`) when `task.task` is eligible for `kill`; otherwise `pi-key-hold` (`hold`).
- `p`: `pi-pause` (`Pause`/`Resume`) when a task is selected and not complete; otherwise `pi-key-pause` (`pause`).
- `s`: `pi-stop` (`Stop queue`) when `task.task` is eligible for `pause`; otherwise `pi-key-stop` (`stop`).
- `y`/`n`: `pi-confirm-ok`/`pi-confirm-cancel` in the confirm row while a confirm is pending; otherwise `pi-key-yes` (`confirm`)/`pi-key-no` (`cancel`).

The holders render as `plain dimColor` with no-op handlers. Their labels are deliberately lowercase: finished tasks must not draw `Abort` or `Pause`, and `pi-confirm-ok` must remain absent without a pending confirm. Always render `j k g i` as no-ops when inapplicable; keep `t` unchanged. History always renders `j k g`.

Keep every existing test unchanged.
