# SPEC: Log guard refusals to the safety log

## Objective
Three guards refuse agent actions without leaving a trace a human can review: the `reference-transaction` ref guard, pi-queue's worktree-busy check, and Claude Code's built-in worktree Bash guard. pi-queue `failed` events also carry no reason. Success: each refusal leaves one redacted entry in the existing safety log (`bash-safety-blocks.jsonl`), visible through `safety-log` and the session-band chip, and every pi-queue `failed` event says why it failed. The follow-up comes from `docs/specs/2026-10-30-pi-queue.md` (items 8, 9 and the reference-transaction open question).

## Decisions (from the grill, 2026-11-03)
- Scope: all three guards. The built-in guard (C) is included only if a probe shows that Claude Code 2.1.317 fires `PostToolUseFailure` or `PermissionDenied` for its refusals.
- One shared writer: `safety-log record`, a subcommand of `scripts/safety-log`. It applies the same redaction, the 4000-character cap and the 2000-entry rotation as the Bash hook. The Bash hook keeps its own `jq` writer unchanged, and a parity test holds both to the same redaction.
- Writers call the shared writer best effort: a failed write never changes a guard's decision, exit code or message.

| Source | `rule` | `command` | `session` | `cwd` | `transcript` | `reason` | First verdict |
|---|---|---|---|---|---|---|---|
| Ref guard | `ref-guard` | the parent git command line, redacted | `CLAUDE_CODE_SESSION_ID`, else `pueue:<PUEUE_TASK_ID>`, else empty | worktree top | empty | the `refused:` line | pending |
| pi-queue | `queue-worktree-busy` | `pi-queue <template>:<step>` | the step's queue session | the step's worktree | empty | `worktree … already runs pueue task N` | pending |
| Claude guard (if the probe passes) | `worktree-guard` | `tool_input.command` | hook input | hook input | hook input | first line of the refusal | `noted` |

- `noted` is a verdict only the logger writes, as an ordinary record in `bash-safety-verdicts.jsonl` straight after the entry. A later `safety-log mark` overrides it; `mark` still accepts only `ok` and `false-positive`. The chip's pending count and `safety-log --pending` skip `noted`.
- No entry when `AGENT_REF_GUARD=off`, or for anything a guard allows.
- Every other pi-queue failure gets a `reason` field in `events.jsonl` only. `/pi` does not show reasons; `events.jsonl` and `pueue log` are enough.

## Boundaries
### Always
- Logging is best effort: no guard's decision, exit code or message changes
- Redact before writing; never log a secret the Bash hook would redact
- Run `~/dotfiles/scripts/spec check SPEC.md` and `~/dotfiles/scripts/floor-guard` before claiming done
### Ask first
- New dependencies; any change to `enforce-bash-safety.sh` or to what any guard allows or refuses
- Settings changes beyond registering the one worktree-guard logging hook
### Never
- Weaken or bypass a guard to make logging or a test easier
- Edit a `verify:` line or a test to make a check pass
- Push to main, merge, approve the spec or a review, force-push

## Open Questions
- If the probe shows no event fires: AC-10 cannot pass as written. Default: the human revises AC-10 to manual ("not hookable in Claude Code 2.1.317") and re-approves before implementation, and the doc records the result.
- What counts as the guard's wording? Default: the error text contains `is isolated in the worktree`; any other failure is not logged.
- `PermissionDenied` and `PostToolUseFailure` both fire? Default: register only the one the probe shows carrying the refusal text.
- Does the ref guard's `python3` call slow commits? Default: it runs only on a refusal, so allowed updates never start Python.
